# SimBridge Flutter Client

A Flutter mobile client for the SimBridge server: browse available iOS
Simulators / Android Emulators, connect to one, mirror its screen, and
control it — touch, swipe/pinch/long-press gestures, device buttons
(home/back/lock/volume/screenshot/…), GPS injection, clipboard sync, and
screen recording — all over the REST + WebSocket protocol described in
`flutter-client-api.md`.

## ⚠️ Please read before you judge "does this compile" on my word alone

This project was written in a sandboxed environment **without a Flutter or
Dart SDK available** — network egress here is restricted to a small
allowlist (npm/pip/crates/GitHub-style hosts) that doesn't include the
Google Cloud Storage host Flutter's SDK and prebuilt engine ship from, so
`flutter pub get` / `flutter analyze` / `flutter test` / `flutter build`
could not actually be run before handing this to you.

What I *did* do instead, by hand, without a compiler:
- Checked every file's braces/parens/brackets balance
- Checked every relative `import '../...'` resolves to a real file on disk
- Checked every symbol used across files (provider methods, model
  constructors, enum members) against where it's actually defined
- Walked every `switch` statement for Dart's fallthrough rules (this is
  how I caught and fixed a real bug — `ConnectionProvider._handleMessage`
  was missing `break;` statements)
- Cross-checked payload shapes against every JSON example in the protocol
  doc

That's a solid substitute for a syntax/reference check, but it is **not**
the same as a green `flutter analyze` and `flutter test` run, and it can't
catch everything a real compiler would (subtle API signature mismatches
in Flutter/package APIs, for instance). Please run the two commands below
yourself before you trust this in production, and if something doesn't
compile, it's genuinely useful feedback — I'd rather you find out from
`flutter analyze` than from me asserting it's fine.


## One-time setup (do this first)

I've delivered the Dart **source** (`lib/`, `test/`, `pubspec.yaml`,
`analysis_options.yaml`) — the part with all the actual logic. I have
*not* hand-written the native Android/iOS project scaffolding
(`android/`, `ios/`, Gradle files, the Xcode project). That scaffolding
is generated by the `flutter create` tool itself, and hand-writing an
Xcode `.pbxproj` file in particular is the kind of thing that looks
plausible and then silently fails to open in Xcode — the real tool does
this far more reliably than I can by hand. So:

1. **Unzip this archive** into an empty folder, e.g. `simbridge_client/`.
2. Move the contents *out* temporarily, or just run `flutter create` in
   the parent directory pointed at this folder:
   ```bash
   flutter create --project-name simbridge_client --org com.yourcompany .
   ```
   Run this **inside** the unzipped `simbridge_client/` folder. Flutter's
   `create` command is safe to run on top of an existing `lib/`,
   `pubspec.yaml`, etc. — it only adds the `android/`, `ios/`, `web/`,
   `macos/`, `linux/`, `windows/` platform folders and a couple of
   top-level files (`.gitignore`, `.metadata`) if they're missing. It
   will **not** overwrite the `lib/`, `test/`, or `pubspec.yaml` content
   in this archive as long as you keep the same `--project-name`.
   - Replace `com.yourcompany` with your own reverse-domain identifier
     (used as the Android/iOS bundle ID).
3. Install dependencies:
   ```bash
   flutter pub get
   ```
4. Verify:
   ```bash
   flutter analyze
   flutter test
   ```
5. Run it:
   ```bash
   flutter run
   ```
   (with a simulator/emulator or physical device selected, same as any
   Flutter app)

If `flutter create .` complains the directory isn't empty in some Flutter
version, the fallback is: run `flutter create --project-name
simbridge_client /tmp/scaffold_only`, then copy just the `android/`,
`ios/`, and (if you want them) `web/`/`macos/`/`linux/`/`windows/` folders
from `/tmp/scaffold_only` into this project.

## Using the app

1. **First launch → Onboarding.** Enter your SimBridge server's host/IP
   and port (defaults to `8080`), whether to use TLS, and a name for this
   device. This is stored locally (`shared_preferences`) and only asked
   once — change it later from the settings gear icon.
2. **Simulator list.** Pulls `GET /api/v1/simulators` and shows each
   simulator/emulator with its platform, OS version, and live status
   (available/busy/offline/error). Pull down to refresh. Tap one to
   connect.
3. **Connecting** does two things in sequence: `POST /api/v1/sessions`
   over REST to register the session, then opens the WebSocket and sends
   `ConnectSimulator` with your configured stream quality/fps/audio
   settings.
4. **Control screen:**
   - The mirrored screen renders incoming `ScreenFrame` messages
     (base64 JPEG/PNG). It's wrapped to the simulator's exact aspect
     ratio so there's no letterboxing to account for in touch mapping.
   - **Touch**: every finger down/move/up is forwarded live as a
     `TouchEvent`, mapped from the widget's local coordinates into the
     simulator's screen-space coordinates (following the doc's example:
     1080×1920 simulator, 400×800 widget, touch at (200,400) → simulator
     (540,960)).
   - **Gestures**: a single-finger drag past ~24 logical pixels sends a
     `Gesture`/`swipe` (up/down/left/right + distance); a two-finger
     pinch sends `Gesture`/`pinch` (+ scale); a long-press sends
     `Gesture`/`long_press` (+ mapped position). These are sent
     *alongside* the raw touch stream, not instead of it, since the doc
     defines them as separate message types — useful if your simulator
     backend only exposes high-level gesture commands rather than raw
     multitouch injection.
   - **Device button bar**: home, back, app switcher, rotate
     left/right, volume up/down, mute, lock/unlock, shake, screenshot.
   - **GPS sheet**: type coordinates or tap a city preset, sends
     `GpsUpdate`.
   - **Clipboard sheet**: type text (or pull from this device's own
     clipboard) and send `ClipboardSync`.
   - **Recording sheet**: start/stop recording (`StartRecording`
     `StopRecording`), shows live status/duration/size from
     `RecordingStatus`.
   - Incoming `Notification` messages show as a dismissible banner;
     `MetricsUpdate` (fps/latency/CPU) shows as a small overlay chip;
     `Error` messages surface as a snackbar.
   - The colored dot in the app bar reflects the live WebSocket state
     (green = connected, orange = connecting/reconnecting, red =
     disconnected).
5. **Reconnection**: if the WebSocket drops, it retries with exponential
   backoff starting at 1 second, doubling up to a 30-second ceiling (per
   the doc), and automatically re-sends `ConnectSimulator` once
   reconnected so the session picks back up.
6. **Settings**: server address/TLS, device name, stream quality/fps/
   audio, and light/dark/system theme.

```

  models/

    api_exception.dart
  providers/
    settings_provider.dart      Persisted server/device/stream settings
    simulator_list_provider.dart
    connection_provider.dart    Orchestrates one active session end-to-end
  screens/
    onboarding_screen.dart
    simulator_list_screen.dart
    control_screen.dart         Mirror + touch/gesture/buttons/GPS/clipboard/recording
    settings_screen.dart

    metrics_chip.dart, notification_banner.dart

    backoff.dart                Exponential backoff calculator (unit tested)

  models/    ws_envelope, simulator, client_payloads JSON round-trip tests

```

## Notes on scope / what's deliberately simplified

- **WebRTC**: the protocol doc's own "Backend Limitations" section says
  WebRTC screen capture integration is still pending server-side, and
  recommends JPEG-over-WebSocket for Flutter clients today — so that's
  what this client actively uses. The WebRTC signaling payload models
  (`WebrtcOffer`/`WebrtcAnswer`/`WebrtcIceCandidate`) are fully modeled
  and ready in `shared_payloads.dart` for whenever that lands.
- **File transfer**: `FileTransferPayload` is modeled (chunked
  upload/download per the doc), but there's no file-picker UI wired up
  yet — add a `file_picker`-style flow calling that payload when you're
  ready to expose it.
- **Motion/heading**: `MotionUpdatePayload`/`HeadingUpdatePayload` and
  `ConnectionProvider.sendHeading(...)` exist; there's no live
  device-sensor UI wired up (no `sensors_plus` dependency was added, to
  keep the dependency list minimal and everything I could review by
  hand) — wiring real accelerometer/compass data in is a small addition
  if you want it.
- **Auth**: the doc says auth isn't enforced in the current server build;
  `PairRequest`/`AuthRequest` models exist and `WebSocketService` has the
  hook (`onConnected`) to send them once you're ready to turn auth on.
